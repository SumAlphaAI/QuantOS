# ADR: X03 atomic local command authority

Status: implemented for local development; target deployment and ProjectUser acceptance pending.

The historical issuer accepted `release_valid`, `kill_switch_engaged`, unverified caller identity and public approval/command hashes. These interfaces remain explicitly labeled compatibility fixtures. X03 exposes a separate `AtomicCommandIssuer` and `SignedCommand`; there is no conversion that launders a legacy checksum into signing authority, and no new HTTP or venue route.

A trusted backend resolves an actual R04 `TradeProposalRecord` and an F06 `AuthContext`. Registration validates R04's schema, non-executable flag, canonical artifact hash, tenant/workspace, originator, account/symbol/release, action/quantity/notional and expiry. It pins the complete record and a concrete X02 intent, including command key, price and Paper/Shadow target. A proposal ID cannot change its pinned contents. Hashes detect drift; they do not authenticate a client or establish the provenance of an external repository. An adapter must resolve the record and current source facts server-side; neither an HTTP assertion nor an Agent is a trusted resolver.

Approval transitions are revision-CAS operations: Pending to Approved, Rejected or Cancelled; Approved to Cancelled; successful issuance to Consumed exactly once. Only the requester cancels. Owner/Approver with the scoped approval capability may approve or reject, except both requester and proposal originator are forbidden. Deadlines are effective immediately, without a background scheduler; status retains the last stored state after expiry, and every mutating/consuming operation rechecks time. Terminal states never revive. Risk approvals are keyed X02 tokens, bound to requester/account/complete intent and at most 60 seconds; an unkeyed signature or arbitrary nonempty text is insufficient.

All issuer mutations acquire its shared mutex first. `RiskGuard::with_current_allow` then holds the same mutex as risk evaluation and kill CAS. It authenticates the exact stored Pre Allow, current identity, time, policy, intent and kill revision, and reruns every risk rule against current X01 snapshot, financial/day/quote facts, venue, S03 release and stored approval token. Only the original reservation's duplicate predicate is suppressed, after its identity and signature have been checked. Risk decision consumption is scoped to one issuer instance; another issuer sharing the guard cannot issue the same decision. Rejected callbacks reserve no consumer.

Inside this critical section, the issuer validates idempotency and approval state, signs the complete command, prepares its audit event, consumes approval and inserts the command. No fallible operation follows these mutations. Clones share state. Cached requests recheck current risk/approval and cannot extend the signed expiry. Different requester/proposal/decision/approval or venue conflicts; expiry, stale data, release invalidation and any kill revision reject even cached commands. Expiry is the minimum of configured TTL (1–60 seconds), proposal, original and current risk deadlines, including all source/release/approval bounds. Command and audit HMAC-SHA256 domains differ; command ID and complete payload are covered. Keys are injected synthetic local material in tests and are never Debug/Serialize.

The audit is an ordered HMAC chain with previous-record hashes. Successful registration, requests, transitions, issuance and replay, and issuance refusals after obtaining the issuer state lock are recorded. Issuance audit and approval/cache mutation share the transaction. `verify_audit` checks the complete current in-memory chain, including its head/length; it is not a durable external audit anchor. `verify_command` checks current local authenticity, stored membership, identity, expiry and kill revision. A consumer still needs its own current-source/revocation and single downstream-submit boundary, owned by TP07; this API performs no submission.

The local contract requires a fresh 42-node/138-group candidate: 41 prerequisite nodes/135 groups, followed by 3 own groups. The S2 prefix is executed first even though X03's graph lists R04 first; manifests retain the graph's canonical topological order. All checks come from one candidate/attempt. The recorder restores historical canonical bytes/existence and publishes only X03 local readiness. Shared changes withdraw X02's prior independent readiness; its history stays untouched.

This is a process-local linearizable implementation, not a crash-safe distributed transaction. Independent guards, restarts or replicas do not share state. Real R04/F06/source trust, key custody/rotation, durable Supabase transactions/RLS, startup fail-closed behavior, record capacity/retention, cross-process crash/recovery/kill propagation, current strategy revocation and TP07 downstream consumption remain target obligations. The original P95 <200ms, security/load/soak, same-SHA hosted CI and all inherited source/legal/target requirements stay NOT_RUN. The 1000-request test uses 1000 simultaneously released Tokio tasks on 16 native workers and proves correctness; it is not a representative latency campaign. No local database or external publication is introduced.

The first X03 closure retained a TP01-C manager child with null exit at the legacy 180-second budget, after captured assertions passed and at doc-tests. Its v1 receipt omitted error/signal diagnostics, so the historical termination remains UNKNOWN with a suspected timeout, never PASS. Current TP01-C v2 evidence requires exact check budgets, elapsed time, timeout/error/signal fields and normal zero exit. The complete manager suite receives a bounded 600-second harness budget; other child checks retain 180 seconds and the outer group 900 seconds. Product performance goals, all test cases and release obligations are unchanged. A new frozen candidate must rerun the entire 42/138 closure.
