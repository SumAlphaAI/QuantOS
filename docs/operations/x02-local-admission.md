# X02 risk and kill switch local admission

`X02_LOCAL` admits only CORE:X02 local engineering functionality. Freeze a clean committed candidate, use `staticEnvironment` and the repository-pinned pnpm 10.20.0, then `make x02-assess-local`. It runs the complete 41-node/135-group closure: X01, S03, F06 and S2 with all dependencies (40 nodes/131 groups), then four own groups. Three independent builds, whole-workspace lint/test, inherited functional suites and current rule coverage execute on that candidate. Historical READY is not an input. Only X02 is published; changed shared inputs withdraw X01's old independent admission while preserving its historical evidence. The recorder restores canonical bytes/existence and publishes the manifest and both plans transactionally.

The public typed API is `quantos_risk::guard::RiskGuard`. Construct one service authority per configured tenant/workspace and share its clones. `evaluate` performs Pre or Post risk evaluation using an F06-authenticated `AuthContext`, a concrete `TradeIntent`, a validated X01 `RiskInputSnapshot`, a real S03 `StrategyRelease`, and trusted backend `AccountFinancials`/`VenueState`. Do not deserialize client assertions into these trusted inputs. Source digests do not authenticate external financial or venue data. Account equity, today's realized P&L, UTC day, quote unit and source timestamp/reference are explicit; lifetime portfolio P&L never supplies today's loss. Snapshot and every open-symbol mark are validated with the authority clock on every evaluation. Release integrity/approval, tenant/workspace, requested Paper/Shadow target, mode, Release universe and current authorization expiry are checked. Assisted Live is outside this API's allowed target type.

All 15 rule predicates run on every evaluation. Invalid identity/numbers, decimal syntax/precision, global/account kill, release, portfolio freshness, financial day/source, venue, duplicate, per-order notional, leverage, concentration and daily loss deny; denial dominates approval. Notional is computed from quantity and price, never trusted from a client-provided scalar. Zero, negative, non-finite, exponent, whitespace and malformed decimal inputs refuse. Projected pre-trade exposure is conservative gross plus absolute order notional, even for reducing sells; netting/hedging is not inferred. Post-trade uses the actual current snapshot gross/symbol amounts and an explicit daily ledger value. A post decision audits the resulting state; it does not suppress or undo a fill.

`RiskPolicy` validates finite positive limits, precision scales <=18, concentration <=1, freshness 1..3600s and decision TTL 1..60s. Every `GuardDecision` contains identity, phase, intent hash, X01 input hash, financial/venue/release/approval facts hash, full policy, kill revision, verdict, all rule outcomes/limit IDs and exact validity interval. HMAC-SHA256 covers the entire payload with domain separation for decision, approval and kill receipt. The application supplies a nonzero 32-byte key and key ID from its trusted bootstrap; key material is neither serialized nor Debug. Local tests use an owned synthetic key, not production credentials. Public verification proves possession of that key, not deployment identity or legal/trading authority. The older `RiskEngine`/`RiskDecision` remains a compatibility fixture API with a content-hash checksum; it cannot satisfy X02's signed authority gate and must not be used for command permission. The old portfolio adapter now requires a separate explicit daily P&L value.

`approve` requires scoped F06 STRATEGY_APPROVE and Owner/Approver identity distinct from the requester. Tokens bind tenant/workspace/account/requester/approver, full intent including command key and release/target, issuance and expiry <=60s. A token cannot override a hard deny. Approval-required and denied inputs do not reserve pre-trade keys; an approved retry may proceed, and only one successful pre-trade admission per account/key is possible through this authority. Post keys are a separate namespace. The caller must retain deterministic fill/review IDs. Durable dedupe/approval consumption and atomic command issuance belong to X03/target integration.

`set_kill_switch` is the kill API: Global (all accounts within this configured service authority) or Account; expected revision CAS; reason and monotonic trusted timestamp required. Scoped Owner/Operator with EXECUTION_OPERATE may engage; only Owner may disengage. Account-bound contexts cannot change Global or another account. Evaluation, revision changes, duplicate admission and receipts share one mutex across all clones. After an engage call returns, all later evaluations through that authority deny. Earlier Allow decisions are invalidated by any revision change, including a later disengage. `validate_allow` rechecks trusted identity/capability/role, exact stored signed decision, intent, policy, time, revision and current switches. Decision expiry is capped by every input's effective age, venue/financial time, S03 approval/evidence and supplied approval expiry; short-lived decisions cannot outlive old data. This API validates risk only. X03 must atomically combine current validation with its issuer/approval consumption; checking then separately issuing a venue command is not admitted here.

The service's state is process-local: kill history, signatures, keys and dedupe are not a durable or distributed service. Restart must never be treated as safe recovery into a live issuer. Multiple independently constructed authorities do not share switches. A deployed authority topology, durable fail-closed startup, trusted identities/clocks/financial sources, secret custody/rotation and record retention/capacity require separate target validation. No database service, credential, HTTP endpoint, order submit or external connection is introduced by this local profile.

`make x02-check` runs the nine meaningful integration/API tests (50 Allow, 50 ApprovalRequired plus valid approvals, 60 Deny, all rule outcomes, tamper/binding/freshness, concurrent duplicates/CAS and clone propagation), legacy issuer/evidence compatibility and policy negatives. `scripts/x02-coverage.mjs <isolated-output>/receipt.json` runs installed nightly `cargo llvm-cov --branch` and retains raw instrumented data/logs. The >=95% denominator is executable rule branches in `crates/quantos-risk/src/rules.rs`, not an enum count, function coverage or whole-crate coverage. Guard authorization/parsing/crypto/clock paths have separate negative tests; the rule percentage is not a whole-runtime coverage claim. Failed/missing/altered/raw-mismatched or non-rule reports cannot pass.

`make x02-local-check` verifies all fresh receipts; `make x02-release-check` must deny without independent target/Beta evidence and ProjectUser confirmation. All 23 inherited target groups plus `x02-target` are NOT_RUN. `x02-target-check.mjs` deliberately refuses local substitution; it requires a separately authorized deployed campaign. Preserve the original P95 <1s target: threaded local correctness is not representative P95 or cross-process proof. Actual Supabase/RLS, BFF/Runtime/issuer integration, durable recovery, real account/venue/source permissions, latest supply-chain/legal review, security/load/soak, same-SHA hosted CI and formal acceptance remain NOT_RUN/PENDING. No production credentials, local PostgreSQL/Supabase, Git push or external publication are part of this task.
