# X01 local Portfolio admission

X01_LOCAL admits only CORE:X01 local functionality. Start from a clean committed candidate and run `make x01-assess-local` under `staticEnvironment`, with the installed pinned pnpm 10.20.0 on PATH. The profile strips database/provider/production credentials and target opt-ins and forces offline package resolution. It creates no PostgreSQL/Supabase service and makes no target connection or external publication.

One complete fresh closure contains exactly 40 nodes/131 unique check groups: F05, R01, S2-SERVICE and their full 39-node dependency closure (127 groups), then X01 model/CLI/schema/policy (4 groups). Three fresh independent builds, make lint/test, the complete inherited functional suites and S2 aggregate are executed on this candidate. Deduplication is only by identical check ID within this one assessment; published historical READY is never an input. X01's recorder retains failures and canonical output deltas and restores original canonical bytes/existence in finally. Its receipt and both plans publish in one rollback-capable transaction. Shared-input changes withdraw the prior independent S2 READY; its historical proof remains available in Git and its original attempt.

The read model rejects gaps, duplicates, invalid identities/symbols/numbers, numeric overflow, backward event/source time and future marks before committing its state or deduplication ID. Missing sequence events can be supplied and the originally rejected event retried. Fill handling supports long/short, partial closes/reversals and fees. Ten thousand fills plus three marks retain the existing golden valuation/P&L; a cold rebuild replays the whole tape. No checkpoint is presented as durable recovery proof.

`apply_recorded(record, portfolio_sequence)` consumes a tenant-wide contiguous source portfolio F05 stream (`aggregate_type=portfolio`, `aggregate_id=<tenant UUID>`, schema v1). It checks the tenant, payload hash, event kind and allowed payload fields. `apply_market_recorded` consumes admitted R01 v2 market events. Both adapters require the caller to explicitly assign the next merged portfolio tape sequence, distinct from each source stream sequence. The caller retains this deterministic tape/order for full rebuild; the read model does not claim to implement durable ingestion/checkpoint scheduling. Quality must be Passed and source identity/schema/times must match. Source event IDs prevent duplicate consumption. The adapter preserves market source time separately from processing time and grants no source/provider permission. Direct JSONL/typed fixture application remains a trusted offline input boundary, not authentication.

`risk_snapshot(account, now, max_age_seconds)` requires an explicit active account-status event and marks for every open position. It includes the full portfolio, account status/time, sorted symbol marks/source event IDs/source times, generation time, age bound and an identity-bound content digest. Each consumer calls `validate_for(expected_tenant, expected_account, trusted_now, allowed_age_seconds)`: missing/stale/future data, disabled/unknown accounts, a looser embedded age bound and altered input are refused. A new event for another symbol cannot refresh an old mark. The old portfolio hash remains compatible and does not bind identity; only the new input hash supplies this binding. Hashes detect alteration; they are not authorization signatures or a substitute for a trusted source.

Projection persistence validates the full snapshot, locks its real tenant/account parent, saves positions/account payload in one transaction and rejects sequence rollback, conflicting content at the same sequence and backward timestamps. Known active/suspended/closed account state and its time are also persisted in `snapshot_json`; legacy unknown states remain explicit. Saved `snapshot_json` is the coherent account query source; `positions_for_account`/`account_state` no longer combine old positions with newer shared marks. A plain snapshot write clears any previous risk input. Only explicit source-time valuation marks update the global cache, never entry-price fallbacks; source times never move backward. Saved snapshots include mark provenance, even for closed or legacy-unknown accounts. The compatible display hash does not authenticate mark provenance; the new risk input hash binds the entire saved payload and provenance. The forward migration adds composite account FKs, payload bindings and a monotonic head trigger, retains forced RLS and member SELECT, and denies member/anon projection writes. Existing NULL payload rows require an authorized rebuild; there is no fabricated backfill. Apply and validate this migration only against the configured authorized Supabase target.

`portfolio-rebuild generate-replay --output <tape>` and `rebuild --input <tape> --golden <reference>` retain their original offline behavior. `--risk-output <file> --risk-at <RFC3339> --max-age-seconds <1..3600>` additionally emits a validated risk input if the tape contains account state. Golden and risk validation precede requested snapshot output writes. Database persistence is an explicit separate opt-in; use the existing configured DATABASE_URL without logging credentials. No X01 local gate invokes it.

`make x01-check` is preflight. `make x01-local-check` validates published local readiness and all fresh receipts; `make x01-release-check` must reject without independent Beta target receipts and ProjectUser acceptance. All 22 inherited target groups plus `x01-target` remain NOT_RUN. `make x01-target-check` explicitly enables ignored `postgres_x01` tests, requires the configured Supabase URL and an applied migration, and must not be called as part of this local task. It tests actual storage/rebuild/conflict/concurrency/RLS; migration syntax/static checks never substitute for its execution.

The model retains f64 valuations and the historical relative 1e-9 golden tolerance; it assumes account valuations use one quote unit and exposes lifetime realized P&L, not daily loss or cash/equity. X02 must apply its own trusted risk policy, equity/day boundaries, authorization and kill switch to validated inputs before making decisions. No order submission or venue command is introduced. UI/BFF/real module integration, trusted deployed clocks and account authority, actual Supabase/RLS/transactions and cross-process recovery, legal/supply-chain review, representative 10000-order/fill replay, 100% rebuild, query P95 <300ms, load/soak and same-SHA hosted CI remain independent target/Beta obligations. Formal user confirmation stays PENDING; local engineering readiness cannot self-approve it.
