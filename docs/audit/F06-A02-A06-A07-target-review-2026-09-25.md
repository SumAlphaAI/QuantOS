## 问题清单及风险分析

1. **阻塞级，A02，Execution 命令入口**：`ExecutionCommandService` 尚未由主进程真实请求路径调用；当前 `main` 只做数据库连接和就绪检查。影响是无从证明签发命令到真实 Vault，再到 kernel 的完整调用，更不能证明发行签名及可信调用方。后续不得开放接受任意 TradeCommand 的 HTTP 路由。
2. **高危，A02，凭据交付边界**：现有进程内服务只把 Vault 结果用作允许/拒绝门槛，并不把明文交给真实 venue adapter；paper kernel 不需要外部凭据。真实 venue 接入时需设计进程内、短寿命且不日志化的凭据传递，并做隔离测试。
3. **低危，A07，平台管理角色例外**：隔离 Supabase 的 `service_role` 具有平台级解密视图访问能力；应用 BFF/Engine/Execution 角色不继承它。它属于受控平台运维例外，不表示普通应用角色可以直接读 Vault。

## 整改建议

1. 在后续 TradeCommand 签发/传输阶段实现可信、可验证的内部命令入口；先核验签名、发行者、幂等键及 command/account 绑定，再调用 `ExecutionCommandService::submit`。隔离目标做真实服务会话 + Vault + paper kernel 同一次提交及过期、账户错配、轮换/撤销负向探针，并生成同完整 SHA 回执后关闭 A02。
2. 真实 venue adapter 另行验证凭据只在 Execution 进程短暂使用、不会进入日志、事件、kernel wire payload 或持久状态；配置受限网络出站策略。
3. F06 A03/A04/A05/A09/A10 继续分别复验；尤其 A09 同区域和跨区域性能阈值、A10 总回执未通过前，保持 `FIX_VALIDATION`。
