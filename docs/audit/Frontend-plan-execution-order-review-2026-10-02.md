## 2. 问题台账

### B-01：全量 API 前置与完整业务阶段 Gate 形成阻塞循环

- 严重级别：阻塞。
- 核心计划第 3.1 节（行 165）：完整阶段 Gate 未通过不得进入下一业务阶段。
- 核心计划 U01（行 829–839）及 R1 Gate（行 852–858）：R1 必须包含 P01–P05、Research Web E2E 与 U01 完整验收。
- 前端计划第 4 节（行 267–270）：全部 A1–A6 API ACCEPTED 后才能开始新的前端页面及既有页面真实联调；每项 UI/WEB 的 depends_on 同样引用全量 API。
- 前端计划 BFF-FE-006（行 433）依赖 CORE:X01/X02/X03/X04/TP07；BFF-FE-009（行 483）依赖 CORE:X05。
- 核心计划规定 X3 在 S2 Gate 之后，而 S2 在 R1 Gate 之后。

下列箭头表示“完成左侧需要先满足右侧”，不是建议开发顺序：

```text
R1 完整 Gate
  → U01 / Web Research 页面验收
  → 全部 BFF API 验收（包含 BFF-FE-006、009）
  → X04 / X05 等 X3 能力验收
  → S2 完整 Gate
  → R1 完整 Gate
```

即使前端第 4 节声明 API 阶段不等待其消费页面，也只避免了某些直接任务引用循环，未解除核心计划“完整阶段 Gate 后才准入下一阶段”的循环。类似地，S04 的策略页面与 S2 Gate 也被 X3 API 前置门槛阻塞。既有壳/官网已开发不解除该循环，因为前端计划明确把既有页面真实联调也纳入全量 API 前置要求。

修复方向：必须协调两份计划的阶段准入规则，单纯移动 Markdown 条目不能解决。

### H-01：跨文档准入只写在说明中，没有可验收的依赖单位

- 严重级别：高。
- 前端第 4 节行 271 声明 CORE 只指服务部分，U01/S04/X06 的页面回到 FEP 验收；但核心计划中的这些 ID 是包含页面与 E2E 的完整任务，未定义单独的服务验收 ID/记录或 Gate。
- FEP-2 文字“主要后端依赖”包含 U01（行 893），FEP-3 包含 S04（行 1134），FEP-5/6 包含 X06（行 1303、1767）；相应 depends_on 未表达这些关系。直接照文字要求完整任务先验收，会出现页面依赖自己的完整核心任务；只照 depends_on 执行，则会遗漏文字准入条件。
- FEP-7 文字依赖 R1/S2/X3 Gate（行 1937），depends_on 没有对应 Gate 依赖。
- FEP-8 文字依赖 L01–L04（行 1963），depends_on 只有全量 API 与 FEP-7（行 1959），缺少任何 CORE:Lxx 引用。

修复方向：区分“前置服务验收”与“最终业务总项/页面验收映射”，给每种关系稳定标识及证据入口；不得直接把 U01/S04/X06 完整任务加入对应消费页面的前置条件。FEP-7/8 的核心 Gate/服务准入也应以机器可校验关系表达。此问题是计划表达缺口，本轮未宣称实际运行已绕过准入。

### M-01：里程碑说明与实际末尾验收位置未对齐

- 严重级别：中。
- FEP-0 位于 PRE-01–PRE-06 之前，复审入口也在阶段开头；G0 定义在 P0 末尾（行 253），但行 268 明确其正式 OpenAPI 冻结项要等 A1 完成，故不能将 P0 工作包完成解释为 FEP-0/G0 完整验收通过。
- FEP-1–FEP-6 位于所属窗口开头，已经说明是范围归组、全部子任务与 Gate 通过后才能关闭，这一说明有效；但缺少阶段末尾的独立关闭检查点和签署/证据入口。
- FEP-4 在 I4 定义，市场、订单标记与 Performance 实际跨 I4/I7，排期表说明 G4 在 I7 完成；FEP-5 在 I4 定义，Audit 子任务早在 I2，闭环跨 I4–I6，G5 在 I6 完成。此顺序本身合理，但从上到下读时要回到前面的里程碑复审。
- “第 6.1 节阶段末运行 Gate”的通用说明不能替代每个阶段关闭点的任务/证据清单。

修复方向：开头保留范围说明，阶段末尾放正式验收检查点。P0 设准备检查点，A1 后关闭正式 G0；I1/G1、I2/G2、I3/G3、I6/G5、I7/G4、I8/G6、I9/G7、I10/G8 分别明确关闭位置。各 API 窗口也补 provider 验收检查点；provider 通过和最终 consumer/UI Gate 分开记录。实际 Gate 顺序为 G5 先于 G4，不能按 G 编号强行排序。

### M-02：现有结构校验无法发现上述跨计划问题

- 严重级别：中。
- `scripts/check-development-plans.mjs` 对 CORE 依赖仅检查 ID 在 coreIds 中存在，然后跳过前端的 index/迭代顺序检查。
- 不读取里程碑“主要后端依赖”作为拓扑边；不构建阶段 Gate，也不检查其关闭位置或状态证据。
- 只在内存中把 BFF-FE-003 的 CORE:R04 改为后续 L4 的 CORE:L04，校验仍返回 PASS；原文件未修改。此探针证明校验器不承担跨计划阶段顺序判断，不意味着探针修改是可接受排期。

修复方向：先正式定义服务/UI 验收单位及 Gate 图，再增加跨文档环、后续阶段依赖、缺失准入、阶段末尾关闭点的检查和有意义的负向用例。不能把合法的领域提前实现或范围汇总项误判为完整验收依赖。

## 4. 建议的协调方案与修复顺序

已有“全量 API 前置”要求和核心 v3.18 的完整阶段串行验收要求，目前不能同时原样满足。建议优先保留前者，但必须显式修订核心准入，不能仅靠解释绕过原 Gate：

1. 正式拆分核心的领域服务验收与页面/端到端总验收。定义 R1/S2/X3 的服务准入 Gate，后续服务开发依赖对应服务 Gate；完整阶段 Gate 仍需 U01/S04/X06 及全部原有 E2E 条件，通过时机移至对应前端闭环之后。记录清楚“服务 Gate 通过 ≠ 原完整阶段 ACCEPTED”。
2. 依据拆分后的服务 Gate 推进核心服务，再完成 A1–A6 全部 provider 验收，继续保留 UI/WEB 全量 API 前置要求。
3. 前端窗口保持现有合法拓扑；在 I2/研究、I3/策略、X3 所需执行/审计/运维页面闭环后，关闭映射的核心完整任务与 Gate；I9 前核验全部 Beta 所需核心总 Gate。
4. 补结构化跨文档依赖、每个窗口末尾验收检查点、完整任务/服务子范围的验收边界；最后扩展校验器及负向检查。

另一种方案是保留核心 v3.18 的完整业务阶段串行顺序，改为每阶段“相关 API → 相关 UI → 完整 Gate → 下一阶段”。它会改变此前明确的“全量 API 在全部 UI 之前”要求，因此不能在本轮只检查文档时自行采用。

本轮没有修改以上要求或减少任何验收标准。当前可继续的无冲突工作是 P0 准备任务以及 A1/A2 的正式复审；随后按核心计划验收 R01/R02/研究服务，但不能宣称依现有全量 API 路线可以完成 R1 完整 Gate。
